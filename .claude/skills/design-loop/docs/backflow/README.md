# 心得回流（backflow）

專案踩到、方法本體沒寫的坑，怎麼變成 design-loop 的規則。本文件是回流流程的唯一出處；每次回流的結果記在 `LOG.md`，逐條判定記在 `triage-<版本>.md`。

## 1. 專案端：怎麼記

- 專案 `_design-loop/LESSONS.md` 一條一列：`日期｜站｜發現｜證據｜狀態`。
- 發現照「症狀 → 原因 → 對策」寫，證據寫得出來源（node、檔案、量測數字）。
- 狀態欄只能是：`待升級（建議去向）`、`已升級 vX.Y`、`只適用本案`、`作廢（原因）`、`待觀察`。
- 專案進行中不改方法本體（SKILL.md 鐵律 9）；使用者正在維護 skill 時除外。

## 2. 什麼時候回流

任一條件成立就排一次回流：

- 專案走完 S4（首次建置完成）或結案。
- 同一專案 `待升級` 累積超過 30 條。
- 發現推翻既有規則的坑（例：既有做法會做錯）→ 不等，下一個版本就處理。

## 3. 四關

### 第一關：入口閘門

**先過基本三項**，缺一項就不能判「進」：

| 條件 | 問題 |
|---|---|
| 可重現 | 換一個節點、換一天做，還會發生嗎？ |
| 有對策 | 寫得出「遇到時怎麼做」，不是只有「這裡壞了」 |
| 有證據 | 有量測數字、前後對照或腳本結果，不是印象 |

**再依根本原因分類，決定要幾個案例**（0.4.0 起；取代原本「一律要第二案」）：

| 類型 | 根本原因 | 判斷方式 | 一案就能進？ | 寫入時標示 |
|---|---|---|---|---|
| 機制型 | Figma、CSS、瀏覽器、工具的行為，或數學必然（取整、比例） | 換一個案子，只要做同一件事一定會發生 | 可以 | `實測` |
| 原則型 | 設計判斷的通則（樣式不要借用、三項齊比） | 講得出適用範圍與例外 | 使用者確認後可以 | `實測`＋使用者確認 |
| 慣例型 | 作業習慣、排版位置、命名偏好 | 換一個團隊可能做法不同但也對 | 可以，但寫成「建議做法」 | `建議做法，待驗`；第二案照做沒問題才改 `實測` |
| 決策型 | 這個品牌、客戶、內容的決定 | 換一個案子就不成立 | 不行 | 留專案 |

判定只有四種：

| 判定 | 意思 | 專案 LESSONS 狀態改成 |
|---|---|---|
| 進 | 寫入方法本體（依上表類型標示） | `已升級 vX.Y` |
| 待觀察 | 看起來是機制或原則，但現有證據無法確定根本原因；或原則型但使用者還沒確認 → 等第二個專案 | `待觀察` |
| 留專案 | 決策型，只適用這個專案 | `只適用本案` |
| 作廢 | 後續事實推翻 | `作廢（原因）`；若有改寫版，改寫版照「進」處理 |

分流表每一列都要寫「類型」。

### 第二關：分流（決定寫成什麼形態）

優先順序由上往下，能用上面的就不用下面的：

| 形態 | 什麼時候用 | 去向 |
|---|---|---|
| 程式 | 能自動檢查或自動處理 | `scripts/`，並更新 SKILL.md 腳本表 |
| 驗收項 | 某一站必須檢查的條件 | `core/sN-*.md` 的「驗收」或「驗證」 |
| 流程 | 做法的順序、分工、前置 | `core/sN-*.md`、`core/parallel.md`、`platforms/*.md` |
| 對照表 | CSS 與 Figma 的換算 | `references/css-to-figma.md` |
| 整數規則 | 小數的成因與修法 | `references/integer-rules.md` |
| gotcha | API 或工具的限制 | `references/figma-gotchas.md`（讀取、建構、腳本）、`references/figma-instance-gotchas.md`（instance、變體、覆寫）、`references/capture-gotchas.md` |

### 第三關：去重與泛化

- 同一個根因的多條併成一條原則或一張表（例：resize、clone、swap 都會重設屬性 → 一張「結構性操作」表）。
- 和既有規則重複 → 補證據到既有規則，不新增條目。
- 推翻既有規則 → 直接改既有規則，並在 triage 與 CHANGELOG 寫明「推翻」。
- **去識別化**：不寫品牌名、客戶名、fileKey、node id、截圖、文案；CSS 前綴寫 `xx`，Figma 前綴寫 `{FP}`；專案寫成「Web 案」「APP 案」。

### 第四關：寫入與標記回收

1. 照去向寫入，格式固定：症狀 → 原因 → 對策 → 證據；標 `實測` 或 `待驗`，標首次寫入版本。
2. 單一 reference 檔上限 60 行、SKILL.md 維持一次讀得完；超過就再合併，或把規則升級成程式。
3. 寫 `triage-<版本>.md`：逐條判定表（# 對應 LESSONS 列順序）、合併群組、統計。
4. 更新 `CHANGELOG.md`（寫明專案要不要跟著改）、`VERSION`；README 平台狀態有變就改。
5. 回到專案 `LESSONS.md` 改狀態欄（先備份到 `_design-loop/backup/<日期>_before_lessons_mark/`）。
6. 在 `LOG.md` 加一列。
7. 自查：`grep` 品牌名、前綴、fileKey、node id 在方法本體為 0 筆；新腳本實際跑過一次。

## 4. 版本號

| 變動 | 版本 |
|---|---|
| 只修文字、補證據 | 不升版，記在下一版 CHANGELOG |
| 新增規則、腳本行為改變、平台狀態改變 | 升 minor（0.3.0 → 0.4.0） |
| 專案資料格式（manifest、registry）不相容 | 升 minor，CHANGELOG 寫遷移步驟；1.0 之後改升 major |

## 5. 定期清理

每次發版掃一次：連續三個專案都沒被引用的條目，降級成「待驗」或刪除，記在 CHANGELOG。
