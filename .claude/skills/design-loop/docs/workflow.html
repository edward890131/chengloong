design-loop 工作流

讓 HTML 頁面、HTML Guideline、Figma 設計系統與設計稿 三邊對得起來、驗得出來，而且任何一邊改了，另外兩邊一定跟上。

價值

為什麼要這套

AI 寫網頁很快，但網頁、手冊、Figma 各做各的，兩週後就對不上：手冊寫 48、網站實際 50、Figma 又是 48.5。design-loop 把「對得上」從靠記憶變成靠檔案與腳本。

HTML 當工作媒介

瀏覽器量得到真實樣式，AI 延伸新畫面最快，也能擷取進 Figma。Figma key page 或 APP 起頭的案子，一樣先轉 HTML 再往下走。

三邊有一張對照表

registry.json 把 CSS class、手冊章節、Figma 母版、設計稿串起來；每個畫面有固定的畫面代碼（例：A-01），Figma 變數用 codeSyntax 對到 CSS 變數。改一個元件時，受影響的頁面是查出來的，不是用猜的。

驗收是腳本，不是感覺

token_diff 比數值、figma_audit 掃小數與未綁變數、頁高回歸、同 viewport 截圖並排。過站條件寫死在每一站，沒過就不往下。

設計系統是 Figma 基礎建設

設計稿只能用 Variables 與 Component instance 組成，母版一改、設計稿跟著動；新樣式要走收斂判斷樹，數量不會失控。設計師要調整時在調整區改，AI 套回正式稿並同步三邊。

方法會跟著專案長大

每個專案踩到的新坑先記在專案裡，驗證過再升級進方法本體，所有專案共用同一份、有版本號，每次改版都自動留下紀錄。

1008 → 077 個元件母版的小數，整數化一輪後
264 / 0Figma 變數比對 CSS 的 mode 值／不一致筆數
71 · 9registry 登記的元件母版與設計稿頁數

全景

三邊與中樞

三邊之間的每一個箭頭都是某一站的工作；三邊之間的對照關係全部寫進 _design-loop/。任何一邊改了，就從對照表查出另外兩邊要動哪裡。

站別

S0–S7 各代表什麼

整個專案分成 8 站。S0–S4 是首次建置，開案時依序走一次；S5–S7 是上線後的常駐循環，網站還在改就一直跑。

站階段白話說明主要產出物
S0 統一成 HTML首次建置不管起點是既有網站、Figma 設計稿還是 APP 截圖，一律先變成網頁。網頁量得到真實樣式、截得到每種螢幕寬度，之後也擷取得進 Figma。每個畫面在這一站拿到畫面代碼每頁 HTML、各螢幕寬度對來源的截圖、實測樣式數據、畫面代碼
S1 萃取 Guideline首次建置量出網站現在用了幾種顏色、字級、間距，找出不一致，逐條決定標準（兩個選項都說得通時由使用者拍板），整理成 Ant Design 式手冊與機器讀得懂的 tokensaudit.md 盤點與決策、tokens.json、tokens.css、components.css、16 章 Guideline
S2 頁面對齊首次建置回頭改網站，讓頁面真的引用 tokens，寫死的數值降到 0；再照 page 結構建好 Figma 的各個 page，把對齊後的頁面擷取進「HTML 擷取」對齊後的 HTML、改前改後截圖、Figma page 結構與擷取稿
S3 Figma 設計系統首次建置在 Figma 建一份和 Guideline 章節一一對應的手冊，裡面有 Variables、文字與效果樣式、元件母版3 組 Variables（含 codeSyntax）、元件母版、registry.json
S4 重建設計稿首次建置只用 S3 的元件 instance 把每一頁重組成 Figma 設計稿，放在所屬功能的 page，像素對得上網頁、數值全是整數依功能分 page 的正式稿、DS_GAPS.md 母版待補清單
S5 三邊同步常駐網頁、Guideline、Figma 任何一邊改了，另外兩邊都要跟上，腳本驗過才算完成；hook 會自動記下哪些檔案被改過，設計師在調整區改完也走這一站SYNC_LOG.md 同步紀錄、比對報告
S6 延伸新頁常駐循環依 Guideline 做新頁：能沿用就沿用，真的要新增時登記理由並回報數量新頁 HTML 與設計稿、新增 token 與元件清單
S7 五視角復盤常駐循環每批新頁做完跑 5 輪：規範合規、像素對位、結構與整數、視覺層級（交給沒參與製作的 agent）、邊界情況REVIEW_LOG.md，每輪附證據

Guideline 是中樞：它的資料來自網頁本身（S1 量測），定案後網頁回頭對齊它（S2），Figma 端全部從它往下建（S3、S4）。機器層面把三邊綁在一起的是 tokens.json、registry.json 與 Figma 變數的 codeSyntax。

Figma

Figma page 結構

Figma 檔的 page 分成四區，每一區誰寫、AI 能不能動都是固定的。AI 用 manifest 記的 page id 找 page，不靠名稱；不在 manifest 裡的 page 一律當成設計師的自由 page，AI 不讀不寫。

wireframe 改版時，AI 逐筆對照 wireframe 與 registry 判斷每個畫面怎麼處理：

wireframe 上registry 上判斷做法
代碼、名稱都相同有同一個畫面的內容異動照 S6「wireframe 更新」改這個畫面
代碼相同、名稱不同有換了一個畫面（例：A-03 忘記密碼 → A-03 簡訊驗證）舊畫面標「已移除」，新畫面沿用代碼、當新頁做；結構看起來一樣、可能只是改名的，先問
新代碼沒有新畫面S6 新頁
沒有有畫面拿掉先確認再標「已移除」

代碼會重複使用，所以 SYNC_LOG、REVIEW_LOG、LESSONS 這些紀錄一律寫「代碼＋名稱」（例：A-03 簡訊驗證），舊紀錄才分得出是哪一個畫面。

場景一

開案：從一句話到 S0

在專案資料夾開新的 Claude Code session，說「用 design-loop 開新專案，平台 web」或「平台 app」。不需要手動複製任何範本，skill 會先判斷這是新案還是已經開過的案子。

  • 開案時會問你：專案根目錄、CSS 前綴、專案名；APP 另外問 iOS／Android 要不要差異化、Dark mode 與平板是否確定要做、交接框架。還不確定就不建 mode，只保留結構。
  • 畫面代碼：有 wireframe 就照 wireframe 的編號；沒有的話 AI 依功能分組提案，你確認後寫進 registry。
  • Figma key page 起頭：客戶的 Figma 檔只讀，記在 figma.source_file_key；設計系統與設計稿放另一個檔。稿子本身的不一致照做並記下來，等 S1 決策。
  • APP 設計師只畫一個平台：另一個平台先照版面做，到 S1 做完平台差異表後，改對差異表驗收。
場景二

三邊同步：任何一邊改了之後

上線後最常發生的事。專案進入 S5 後，hook 會把改到的 HTML、CSS、tokens 記進 SYNC_PENDING.md，下次開場會先處理。hook 抓不到的（在 Figma 先改、用別的工具改、設計師在調整區改完），由使用者或設計師說一聲就走同一條流程。

類型判斷至少要動
T token 值改的是 --x-* 本身的值，所有引用處都會變tokens.json、tokens.css、Figma 變數、手冊色票與規格表。AI 主動想改全站 token 值時要先問
C 元件元件改引用別的 token，或結構改變components.css、手冊元件章、Figma 母版、受影響的設計稿
V 新變體新 class 或新 modifierC 類全部加 registry；照 S3 建構規則做，不必重新擷取
P 頁面區塊順序、文案、版型HTML、重新擷取該頁、更新該頁設計稿
G 規範文字用法說明、Do／Don't手冊 parts、Figma 規格文字

Figma 先動的時候：讀出 Figma 上的實際值與綁定，對不到既有 token 的值先問規格，驗母版、更新 registry，再回頭補 components.css 與手冊示範，最後用手冊示範的渲染結果對 Figma 母版驗收。

場景三

設計師在 Figma 調整之後

正式稿裡有元件 instance、變數與樣式綁定，直接改容易打斷綁定，三邊也不會同步。所以設計師不直接改正式稿：複製到調整區改完，跟 AI 說一聲，AI 比對差異後套回正式稿，並同步回 HTML 與 Guideline。

防呆：有人直接改了正式稿

正常做法是走調整區，但有人直接在正式稿改了一句文案，也要抓得到、同步得了，而且不能被 AI 蓋掉。

場景四

延伸新頁與五視角復盤

拿到新的 wireframe 或需求時，AI 依 Guideline 延伸畫面：先做 HTML，再還原成套元件的設計稿，最後用五個固定視角各復盤一輪。重點是能自主往前做，但每一個新樣式都要說得出理由。

判斷樹做法權限
①既有元件直接用自主
②既有元件換變體或屬性值自主
③母版加變體、BOOLEAN、INSTANCE_SWAP，不動既有 key 與屬性名自主
④只用手冊既有的字級、色、線條、間距與子元件組新元件（例：時間軸）自主
⑤新增 token自主，但在 REVIEW_LOG 寫需求、最接近的既有選項、為什麼不行；同一頁超過 3 個先停
⑥帶進手冊沒有的形狀、版型類別或動態（例：斜切卡片、瀑布流）同 ⑤
—wireframe 以外的內容欄位、導覽或資訊架構、全站既有 token 值、一整類新 token停下來問

設計師自己補的畫面：wireframe 上沒有、設計師自己畫的畫面，預設不同步。設計師指定要加進正式區時，當成沒有 wireframe 的新頁照這條流程重做，原稿只當參考，不直接搬進正式區。

分工

Agent 之間的關係

design-loop 讓多個 agent 同時動工也不會互相覆蓋，靠的是兩件事：每一份產物只有一個負責人，而且所有人都把結果寫進同一個 _design-loop/，不存在對話記憶裡。

角色做什麼寫入界線
使用者S1 手冊過目；決定欄位、資訊架構、全站 token 值、整數政策、Figma 檔放置—AI 列選項，決定權在使用者
設計師在調整區改稿、下指令套回；確認正式稿上被直接改過的地方是不是刻意的調整區的副本、自由 page不直接改正式稿；要改元件本身直接跟 AI 說
主 agent開場判斷、站別路由、S0–S2 與 S5 主流程、調整區套回、派工與彙整回報manifest、SYNC_LOG該拍板的事不自己挑
母版負責人S3 建 Variables 與母版、處理 DS_GAPS、S5 的母版修改Figma 母版、registry.components、FIGMA_DS_SPEC同一個母版只有一個負責人；只有一個 agent 時就是它
頁面 agentS4 依擷取稿重建指定頁面自己的 frame、DS_GAPS、頁高不改母版、不碰別人的 frame；Wireframe 與調整區唯讀
R4 審查 agentS7 視覺層級與品質視角REVIEW_LOG 的 R4不給製作過程，只給截圖、基準頁、手冊、禁用清單
量測 agent多頁、多 viewport 平行截圖與 computed stylemeasure/、evidence/Playwright MCP 只有一個瀏覽器，留給主 agent；其他 agent 自裝
另一個 session依產物擁有權分工，例如一邊負責 Variables，一邊負責母版與手機版設計稿自己擁有的產物；共用檔只改自己的列寫共用檔前先重讀；範圍用 SendMessage 講清楚
外部 skillfigma-use、figma-generate-library 提供 Figma API 規則；beta-directions 是上游，產出第一版畫面—API 規則以它們為準，design-loop 只補專案慣例與踩坑
版本

方法怎麼長大

方法本體只有一份，所有專案都讀它、不複製。專案踩到的新坑先記在專案裡，驗證過才寫回方法、升版號；其他專案下次開場會看到版本差異，由使用者決定要不要跟上。

鐵律

鐵律

  1. HTML 是工作媒介，Web 和 APP 都一樣。最後用 Flutter 或原生實作也先做 HTML；APP 的 HTML 是原型，交付的是 tokens.json 與設計稿。
  2. Figma key page 起頭時，HTML 對 Figma 驗收。稿子本身的不一致記下來等決策，不在 HTML 裡偷偷修掉。
  3. 不跳站，但可以驗收過站。已經有手冊或 Figma DS 的專案，跑那一站的驗收，過了才往下。
  4. 狀態寫硬碟，不寫進 Figma。對照關係全部在 registry；Figma 上只寫元件 description。
  5. 整數從建母版就守。鎖比例寬度取倍數、網格餘數照專案政策、奇偶置中用 min-height 補。
  6. 改動一律走 S5。三邊都改完、腳本驗過、SYNC_LOG 記下，才叫完成。
  7. 延伸先沿用。可以自主新增，但要寫理由、回報數量；欄位、IA、全站 token 值要先問。
  8. 復盤是五個視角各一輪。視覺層級交給沒參與製作的 agent。
  9. 新坑先記在專案。驗證過才升級進方法本體。
